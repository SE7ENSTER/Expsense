# SLG Expense code review — 10 November 2026

Scope: the production entry point (`docs/index.html`), its 15 loaded scripts, report load/save, the dashboard and table/history adapters, management and finance actions, registration/user management, notifications, receipt/PDF handling, both repository Firestore rule files, and deployment configuration. Staging files were checked to distinguish candidate fixes from production code; all 31 existing `docs/*.js` files passed syntax checking before this change. This is a repository review, not a verification of the rules deployed in the Firebase console or an authenticated end-to-end audit.

## Findings addressed in this change

- The core dashboard sorted by `updatedAt`, while management rendered the same container using its own dataset and numbering. There is now one dashboard renderer. It sorts saved report numbers naturally, ascending, with document IDs as deterministic tie-breakers; editing timestamps cannot reorder reports.
- Cards and the table previously replaced their contents on repeated refreshes. Identical visible content now retains the existing nodes, buttons and scroll container. The table initializes immediately and responds to actual list changes, rather than switching presentation after a delayed timer.
- `assignReportNumbers()` derived numbers from each viewer's visible subset and recomputed them on reads. It also assigned the calculated values before checking whether persistence was needed. This read-time renumbering and writing have been removed. Saved numbers are preserved. A report with no saved number displays **Not assigned**, sorts after numbered reports by document ID, and requires a separate authoritative numbering/backfill process. This change does not assign or migrate stored report numbers.
- `{id: document.id, ...document.data()}` allowed an embedded client UUID to replace the real Firestore document ID. The core and management report loaders now give the actual document ID precedence. A regression test verifies that saving an existing draft again updates its document rather than creating another one.
- Report numbers are visible in the active table. The company logo is added to both sign-in and application headers, with responsive sizing.

## Open findings, prioritized

| Priority | Finding and evidence | Consequence / next action |
|---|---|---|
| P1 | `firestore.rules:127–143` allows owners to update their report regardless of current status, and Manager/Finance updates are not limited to specific fields or next statuses. Production HTML does not load the candidate `stabilization-lock-validation-v282.js`. | If these repository rules are deployed, submitted/approved reports can be changed and workflow statuses can be bypassed. Verify deployed rules, then test and release UI locking and field/transition restrictions together. Do not blindly publish the candidate rules: the current Finance actions still use legacy statuses. |
| P1 | Core `saveReport()` has no in-flight save guard, and retains a `serverTimestamp()` sentinel in `current.createdAt` after the first write rather than hydrating the saved document. | Concurrent saves can still create duplicate drafts; repeated saves within a session can reset creation time. Use a stable document ID from first save, prevent concurrent writes, preserve server creation time, and return explicit success/failure. The ID-precedence defect is fixed here; this broader save refactor remains open. |
| P1 | `admin-user-management.js` creates an Authentication account before writing another user's profile. `firestore.rules` permits profile creation only for the signed-in user's own UID, while the admin request remains signed in as the admin. | Under those rules, Auth creation succeeds but profile creation fails, leaving an incomplete account. Align account provisioning with deployed rules and use a trusted provisioning operation with failure recovery. |
| P2 | `management-v2.js` queries/processes `Finance Processing`; several other modules use `Reimbursement Processing`; the candidate rules restrict new processing writes to the latter. Budget calculations and queue filters do not consistently recognize both. | Reports can disappear from Finance queues or be omitted from budget usage. Adopt a single canonical status and explicitly map legacy values throughout queries, actions, rules and budgets. |
| P2 | `notifications-v23.js:88–95` schedules notifications after actions without an explicit success result. Save catches errors internally; Manager/Finance actions can return after a cancelled prompt. | Notifications can describe an operation that did not succeed. Make mutation functions return success and emit notifications only for the confirmed report/action, rather than locating the latest submitted report later. |
| P2 | `receipt-dashboard-phase1-v24.js` saves PDF metadata in a delayed second write and keeps a cross-report `pdfMap`; PDF/image data is stored inside the report document. | The UI may report success before the original PDF is saved, and large/multiple receipts can exhaust the document size limit. Save the exact report's receipt references as part of a controlled upload/save operation and move binary content to object storage. |
| P2 | `admin-user-management.js` rewrites the entire user-management form every four seconds. Multiple modules wrap `showView`, `refreshAdmin` and `saveReport` using delayed patches. | Admin input can be lost; behavior depends on initialization timing. Remove unconditional form rendering and replace chained global patches with explicit modules/events in a separate refactor. |
| P2 | Report status updates and their approval/payment log entries are separate writes. | Partial failures can leave a changed status without its audit entry. Use an atomic write batch/transaction and test failures and retries. |
